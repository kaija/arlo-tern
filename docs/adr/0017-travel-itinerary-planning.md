# 0017. 旅遊規劃：獨立的逐日逐時行程，接外部資料來源

- 狀態：已接受
- 日期：2026-11-07（2026-11-11 更新）

## 背景與問題

一般 task 只需要日期與時間；旅遊需要**詳細的每日、每小時規劃**，用戶也要能用 AI 查詢與安排。可行的時間表取決於地點、營業時間、交通時間、航班、住宿與天氣。

原本可用的 Amadeus Self-Service API 已在 2026 年 7 月停止服務。

## 考慮的選項

資料來源：

- Google Maps Platform（Places、Routes、Weather）
- 機票 / 住宿：Duffel、聯盟 API（Booking.com / Expedia 等）
- 天氣：Google Maps Platform Weather API、OpenWeather
- 只用 LLM，不接外部 API

行事曆呈現：

1. 行程時段項目顯示在日 / 週曆上，並可設提醒
2. 只在旅遊頁

## 決策

- 旅遊是 Core API 內獨立的 `travel` 模組，與一般 task 分開
- 行程結構：**旅程 → 每一天 → 依時間排序的時段項目**
- 用戶可在 App 手動編輯，也可以透過 AI agent 查詢與安排（agent 以工具操作行程，見 [0014](0014-personal-agent-shared-memory.md)）
- 外部資料來源：
  - **Google Maps Platform**：Places（景點、餐廳、營業時間）、Routes（交通時間）、**Weather API**（最多 240 小時逐時、10 天逐日預報）
  - **機票 / 住宿**：以 **Duffel** 為評估對象，只查詢、不下單
- 各外部來源以 adapter 封裝，供應商可替換
- **呈現**：行程的逐日逐時細節只在旅遊頁，行事曆上只顯示旅程期間（見 [0016](0016-in-app-calendar.md)）。行程時段項目**不設提醒**

## 後果

### 正面

- agent 排出的行程以真實的營業時間、交通時間與天氣為依據，可行性較高
- 地點、交通、天氣都由同一個供應商提供，用同一份帳單與金鑰
- 旅遊與一般 task 各自演進，不互相拖累

### 負面 / 風險

- 多個付費 API 的成本隨使用量增加
- Duffel 主要以訂單計費，只查詢不下單的用法可能受限，需要先確認
- 不下單，用戶仍需到外部平台完成預訂
- 行程時段項目沒有提醒，用戶可能錯過行程中的航班或預約。需要提醒時要另外建立 task

## 待決

- Duffel 只查詢不下單的使用條件與費用；若不適用，改用哪個供應商
