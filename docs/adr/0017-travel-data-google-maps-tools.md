# ADR-0017：旅遊外部資料用 Google Maps Platform 包成 agent 工具

- 狀態：已接受
- 日期：2026-11-13
- 相關：ADR-0013、ADR-0016、ADR-0022

## 背景

agent 排逐小時行程時，需要景點、營業時間、地點之間的交通時間這些外部資料。只靠模型內建知識，營業時間與交通時間容易出錯，逐小時行程的可信度會很低。

agent 透過 OpenAI Agents SDK 的 adapter 接 Claude（見 ADR-0013），Claude 的原生 web search 工具能否透過 adapter 使用還沒有驗證。

## 考慮過的選項

1. **地圖 API 當工具**：把 Google Maps Platform 包成 function tool。結果是結構化資料，有真實的地點 ID 與座標。
2. **網路搜尋工具**：涵蓋面廣，但結果是非結構化文字，沒有可靠的座標與交通時間，而且原生 web search 能否透過 adapter 使用未驗證。
3. **地圖 API 加網路搜尋**：規劃品質最好，但成本與工具數都增加。
4. **只用模型內建知識**：零成本，但逐小時行程的可信度低。

## 決定

採用選項 1。

- 把 Google Maps Platform 包成 agent 的 function tool（見 ADR-0013）：
  - **地點搜尋**（Places API）：以文字與區域搜尋地點，回傳名稱、地址、座標、地點 ID、類型、評分。
  - **地點詳情**（Places API）：以地點 ID 取得營業時間等細節。
  - **路線時間**（Routes API）：計算兩點之間指定交通方式的預估時間與距離。
- 工具由核心服務代為呼叫 Google API，API 金鑰只存在後端，不放進 App。
- 行程項目保存地點 ID、名稱、地址與座標（見 ADR-0016）。App 以地點 ID 或座標開啟地圖 App 導航。
- 成本控制：
  - 每次請求只要求需要的欄位；
  - 在 Google Cloud 對金鑰設每日配額上限；
  - 對每個用戶的工具呼叫次數做限流；
  - 同一輪 agent 對話內重複的查詢使用暫存結果。
- 送給 Google 的只有地點查詢字串與座標，**不送用戶的對話內容或個人識別資料**。工具的參數由模型產生，system prompt 需指示它不要把個人資訊放進查詢字串。

## 後果

### 正面

- 行程項目有真實的地點與座標，營業時間與交通時間有依據。
- 這些是自家定義的工具，不受 adapter 能否透傳原生工具的限制。
- App 可以直接開地圖導航。

### 負面與接受的風險

- 按次計費。內測規模下費用應該有限，但 agent 的工具呼叫次數不可預測，必須靠配額與限流封頂。實際費率要在啟用前查當時的價目表。
- 多一個外部依賴與委外處理者（Google），要列入隱私政策（見 ADR-0022）。
- Google Maps Platform 的條款對 Places 內容的保存有限制。地點 ID 可以長期保存，其他欄位（名稱、地址、營業時間等）能保存多久，要在實作前對照當時的條款確認，必要時改成只存地點 ID、顯示時再查詢。
- 沒有網路搜尋，agent 拿不到活動、展覽、季節性資訊，也無法查部落格式的推薦；行程的「靈感」來自模型內建知識。
- 交通時間是查詢當下的估計，不代表出發當天的實際狀況。

## 之後可以加強的方向

內測後若需要時效性資訊，再評估加入網路搜尋工具。
