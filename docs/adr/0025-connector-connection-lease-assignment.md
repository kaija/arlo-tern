# ADR-0025：讀取服務以資料庫租約分配用戶連線，支援多容器

- 狀態：已接受
- 日期：2026-11-14
- 相關：ADR-0001、ADR-0002、ADR-0005、ADR-0019、ADR-0020、ADR-0021

## 背景

讀取服務是有狀態的常駐程序，持有每個已連結用戶的 LINE 連線（見 ADR-0019）。ADR-0019 記錄了兩個限制，但沒有決定怎麼處理：

- 同一個用戶的連線同一時間只能由一個實例持有，不能直接水平擴充成多副本。
- 連線數成長後需要分片，這不在 MVP 範圍。

ADR-0021 決定正式上線時轉到 ECS Fargate，讀取服務維持單一實例。檢視多容器的運作方式時，發現這個安排有兩個沒有處理的問題：

1. **單一實例也會出現兩個容器同時執行。** ECS 的 replica service 預設 `minimumHealthyPercent` 是 100%、`maximumPercent` 是 200%（AWS 文件，2026-11-14 查閱）。期望數量為 1 時，部署會先啟動新容器再停掉舊容器。兩個容器在這段時間都會還原所有 session 並登入，同一份憑證被兩個程序同時使用。
2. **超過單一容器的容量後沒有擴充方式。** 每條連線的資源用量要等 linejs 的多連線驗證才知道。之後加入的讀取個人 WhatsApp 對話（whatsapp-web.js，每個帳號一個 Chromium）每個容器能承載的帳號數會少很多。

同一份憑證被兩個程序同時登入會互相擠掉連線，對 LINE 而言也是異常行為，會提高 ADR-0002 記錄的封號風險。所以這裡要保證的性質是：**任何時間點，一個用戶的連線最多只有一個容器持有。**

核心服務的 API 與 worker 沒有這個問題。它們不綁定用戶：API 的請求由負載平衡器送到任一容器，worker 向 job queue 取工作，一個工作只會被一個 worker 取走（見 ADR-0020）。

對齊時說明了固定雜湊分片與資料庫租約兩個做法，建議的是資料庫租約，專案擁有者要求把它寫成 ADR。其餘細節，包含控制介面的路由方式、導入時機、不主動重新平衡、手動調整容器數，對齊時沒有逐項討論，是依一般做法訂的預設設計。

本文件說的「重新連線」是指讀取服務用已保存的 session 還原連線（見 ADR-0019），不是用戶重新掃 QR code。LINE 是否把這種還原視為一次新的登入，尚未驗證。

## 考慮過的選項

分配機制：

1. **維持單一實例，只加大容器規格**：不需要分配機制。但容量受單一容器的上限限制；任何重啟都讓所有用戶重新連線；在 ECS 上還是要另外處理部署時新舊容器重疊的問題。
2. **固定雜湊分片**：每個容器有編號，負責 `hash(user_id) % N` 的用戶。實作簡單、不需要協調。但改變 N 會讓大量用戶換容器並重新連線；ECS 的容器沒有固定編號，要拆成 N 個各一個實例的 service；一個容器停擺時，它的用戶沒有其他容器接手。
3. **資料庫租約**：容器在 PostgreSQL 登記自己並定期續約，認領沒有人持有的連線直到自己的容量上限。容器停擺後租約過期，其他容器接手。
4. **外部協調服務**（Redis、etcd、DynamoDB 的鎖）：成熟，但多一個要維運的元件，違反 ADR-0020 只用 PostgreSQL 的決定。

核心服務怎麼找到持有某個用戶的容器：

1. **查出持有者後直接呼叫它的內部介面**：沿用 ADR-0019 的內部控制介面，只多一步查詢。
2. **改成經由資料庫傳遞指令**：核心服務把指令寫進資料庫，持有的容器取出執行。不需要容器之間的網路可達，但改掉了 ADR-0019 的控制面，連結流程這類需要即時回應的操作會變複雜。

## 決定

分配機制採用選項 3，路由採用選項 1。

### 適用範圍與時機

- **MVP 不變。** 內測在單一 VM 上用 Docker Compose 執行一個讀取服務（見 ADR-0021），部署時是先停後啟，不會有兩個容器重疊。MVP 不實作租約。
- **轉到 ECS 時實作租約。** 讀取服務放上 ECS 之前要先完成本 ADR 的機制，即使一開始只跑一個容器，因為問題 1 在單一實例時就存在。
- **容器數量依實測決定。** 轉到 ECS 時從一個容器開始。每個容器的容量上限依 linejs 多連線驗證的結果訂定，做成設定；連線數接近上限時再加容器。
- 之後加入的其他平台連線（讀取個人 WhatsApp 對話）使用同一套機制，容量上限各自設定。

這修訂了 ADR-0021 的一項後果：「應用程式轉 ECS 時不需要改程式」對讀取服務不再成立。ADR-0021 的其他決定不變。

### 租約

- **容器登記。** 每個讀取服務容器啟動時產生一個實例識別碼，在資料庫登記一筆資料：內部位址、容量上限、租約到期時間、狀態（服務中、排空中）。
- **租約記在容器上，不記在每條連線上。** 連線只記錄「目前由哪個實例持有」。續約每次只更新容器自己的那一筆。
- **續約。** 容器定期延長自己的租約。到期時間一律用資料庫的時間計算，不用容器的本機時間。
- **認領。** 容器認領「沒有持有者」或「持有者的租約已過期」的連線，直到自己的容量上限。認領在資料庫交易內完成，同一條連線只會被一個容器認領成功。認領後的重新連線沿用 ADR-0019 的規則：分批、帶隨機延遲。
- **自我隔離。** 容器在租約到期前的安全間隔內還無法確認續約成功時，必須自己關閉手上所有的連線，不等別人來接手。資料庫連不上時也是如此。
- **寫入要檢查持有權。** 容器寫回 session 與憑證時，條件必須包含「這條連線仍由我持有」。條件不成立就停止該連線，避免過期的容器覆蓋新持有者更新過的 session。
- **訊息入庫不需要額外處理。** 交接期間兩個容器收到同一則訊息時，既有的唯一約束（同一則訊息不重複入庫，見系統設計文件第 4.2 節）已經涵蓋。
- 續約間隔、租約長度、安全間隔、每個容器的容量上限都是設定，不寫死在程式裡。

### 部署與容器數量變動

- **正常停止。** 容器收到停止通知時進入排空：停止認領、關閉手上的連線、釋放持有權，然後結束。新的容器可以立刻認領被釋放的連線。排空必須在 ECS 給的停止寬限時間內完成；Fargate 的 `stopTimeout` 預設 30 秒、上限 120 秒（AWS 文件，2026-11-14 查閱）。來不及釋放的連線由租約過期處理。
- **異常停止。** 容器沒有排空就消失時，它的連線在租約過期後由其他容器認領。這段時間這些用戶的訊息不會被讀取。
- **健康檢查不能以「持有連線」為條件。** 滾動部署時，新容器要先被判定為健康，舊容器才會被停掉並釋放連線。健康檢查只看程序是否正常、資料庫是否連得上。
- **不主動重新平衡。** 新加入的容器只認領沒有持有者的連線，不從其他容器搬走連線，因為每次搬動都讓該用戶的連線中斷後重新連線。要減少容器時，讓要移除的容器排空。
- **容器數量手動調整，不用自動擴縮。** 理由同上：容器數量的每次變動都伴隨一批重新連線。

### 控制介面的路由

沿用 ADR-0019 的內部控制介面，核心服務多做一步查詢：

- **已連結的用戶**（中斷連結、變更讀取範圍）：核心服務從資料庫查出持有該連線的實例與它的內部位址，直接呼叫它。
- **新的連結**：核心服務挑選服務中、剩餘容量最多的實例發起連結流程。連結流程進行中的狀態在那個容器的記憶體裡，所以連結流程要記錄負責的實例，後續的查詢與取消都送到同一個實例。連結成功後由該實例持有這條連線。
- **連結流程進行中容器停擺**：該流程標記為失敗，用戶在 App 重新發起。
- **找不到持有者，或持有者沒有回應**：連線還沒被接手時，核心服務把請求交給任一個服務中的實例，由它先認領再執行；持有者暫時沒有回應時回報可重試的錯誤。
- 讀取服務仍然不對外網開放，這個介面仍然沒有任何發訊、已讀、加好友、改設定的方法（見 ADR-0001）。

### 不在本 ADR 範圍

核心服務 API 開多副本時，agent 串流斷線後重連到另一個容器、以及限流不能只靠程序內狀態這兩件事，與用戶分配無關，本 ADR 不做決定。

## 後果

### 正面

- 「一個用戶的連線最多一個容器持有」由資料庫保證，部署時新舊容器重疊不再造成同一份憑證被兩個程序登入。
- 讀取服務可以加容器擴充容量，一個容器停擺時其他容器會接手它的用戶。
- 增減容器時只有被交接的用戶需要重新連線。
- 只依賴 PostgreSQL，不增加元件（見 ADR-0020）。
- 沿用 ADR-0019 的內部控制介面。

### 負面與接受的風險

- **租約擋不住已經開著的連線。** 租約只管資料庫裡誰算持有者。一個被暫停或與資料庫斷線的容器，在它察覺並自我隔離之前，手上的 LINE 連線還開著；這時租約如果已經過期並被別的容器認領，會有一小段時間兩個容器同時登入。自我隔離與安全間隔把這段時間壓到很短，但無法保證為零。這是 ADR-0002 封號風險的一部分。
- **資料庫不可用時所有連線都會關閉。** 每個容器都無法續約而自我隔離。這段時間訊息本來就無法入庫，但恢復後所有用戶的連線要重新建立一次。
- 容器異常停止時，它的用戶在租約過期前沒有人讀取訊息；這段時間的訊息能否補收取決於 linejs 的行為（見 ADR-0021）。租約長度是「接手速度」與「誤判容器已停擺」之間的取捨。
- 讀取服務多了登記、續約、認領、排空、持有權檢查這些邏輯，是容易出錯的併發程式，需要針對交接與斷線情境的測試。
- 核心服務需要能直接連到個別的讀取服務容器，內部網路與安全群組要允許；位址登記在資料庫，容器重啟後位址會變。
- 不主動重新平衡，容器之間的連線數可能不平均，要靠手動排空來調整。
- 容器數量手動調整，連線數成長時要有人監看容量並加容器。
- 連結流程進行中容器停擺，用戶要重新掃一次 QR code。

## 待確認

- 把 `minimumHealthyPercent` 設為 0、`maximumPercent` 設為 100 是否能讓 ECS 先停後啟。AWS 文件沒有直接描述這個組合的行為，是從計算方式推論的。有了租約之後不依賴這個設定，但可以作為轉換初期的額外保護。
- linejs 在登入後被另一個程序用同一份 session 登入時的實際行為（哪一邊被登出、session 是否失效），用來評估「兩個容器短暫同時登入」的實際後果。在實作租約之前驗證，不屬於 MVP 的技術驗證。
- 租約長度、續約間隔、安全間隔的初始值，以及每個容器的容量上限，在實作時依 linejs 多連線驗證的結果訂定。
- 排空一個滿載的容器需要多久，是否能在 Fargate 的停止寬限時間內完成。
