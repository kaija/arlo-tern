# 0019. 可疑訊息偵測與警告

- 狀態：已接受
- 日期：2026-11-07（2026-11-11 更新）

## 背景與問題

讀取用戶訊息的服務讀到可疑訊息時，要透過官方帳號發警告通知用戶。誤報太多會讓用戶忽略警告，漏報則可能造成財務損失，所以需要可量測的偵測方法。

## 考慮的選項

偵測方法：

1. LLM 判斷 + 網址信譽查詢
2. 只用 LLM

評估方式：

1. 標註資料集 + 用戶回報
2. 只靠用戶回報

## 決策

- **偵測範圍**：
  - 詐騙 / 假冒（假親友借錢、假客服、投資詐騙等）
  - 釣魚連結（惡意或仿冒網址）
  - 可疑付款要求（要求匯款、購買點數卡、提供驗證碼）
- **偵測來源**：LINE、WhatsApp（含群組，見 [0009](0009-line-whatsapp-unofficial-read-only.md)）與 Gmail（見 [0008](0008-gmail-access.md)）
- **偵測方法**：
  - LLM 判斷訊息內容的意圖（模型見 [0013](0013-llm-provider-abstraction.md)）
  - 訊息中的網址另外查詢 **GCP Web Risk API**
  - 兩者任一判定可疑，就發出警告
- **評估**：
  - 建立標註資料集：台灣常見的詐騙樣本與正常訊息
  - 換模型或 prompt 時，用資料集量測準確率與召回率
  - 警告上提供「不是詐騙」回報，用戶回報作為持續校正的依據
- 偵測在 Processing worker 執行（見 [0002](0002-system-decomposition.md)）
- **警告通道**：
  - 來自 LINE 的可疑訊息：透過 LINE OA 警告
  - 來自 WhatsApp 的可疑訊息：透過 WhatsApp 官方號警告
  - 來自 Gmail 的可疑郵件：透過用戶指定的官方帳號警告
  - 同時發送 App 推播
- 所有警告都經官方 API 發出（見 [0012](0012-official-accounts.md)），絕不透過用戶的個人 session 發訊
- 警告紀錄保存來源參照 ID，不保存原文（見 [0011](0011-no-raw-message-retention.md)）

## 後果

### 正面

- 用戶在收到可疑訊息的同一個平台就看到警告，最即時
- Web Risk 的網址黑名單能補上 LLM 看不出來的惡意網址
- 有標註資料集，換模型時有客觀的比較依據

### 負面 / 風險

- 任一判定即警告，誤報率會比較高
- 標註資料集要持續更新，才能跟上新的詐騙手法
- 標註資料集本身含訊息內容，需要去識別化，並與 [0011](0011-no-raw-message-retention.md) 的「不保存原文」分開處理
- WhatsApp 警告需使用預先核准的範本訊息（見 [0012](0012-official-accounts.md)）
- 用戶若沒有綁定對應平台的官方帳號身分，就只能收到 App 推播

## 待決
