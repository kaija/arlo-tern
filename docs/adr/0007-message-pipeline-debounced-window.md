# ADR-0007：訊息管線依對話做短視窗合併

- 狀態：已接受
- 日期：2026-11-13
- 相關：ADR-0006、ADR-0008、ADR-0009、ADR-0010、ADR-0020

## 背景

讀取服務收到訊息後，要送 LLM 做 task 抽取與詐騙判定。處理節奏影響三件事：警告的即時性、LLM 呼叫量、判斷的準確度。單獨一句話常常不成 task（「好」「那就週五」），要看前後文才能判斷。群組洗版時逐則處理會讓呼叫量暴增。

## 考慮過的選項

1. **依對話做短視窗合併**：同一個對話的訊息先排隊，等對話安靜一小段時間再連同前文一次送 LLM。
2. **每則訊息即時處理**：警告最即時，但呼叫量大、單句缺前後文、容易重複產生 task。
3. **詐騙即時、task 定時批次**：成本最低，但當天的 task 來不及提醒，而且要維護兩條管線。

## 決定

採用選項 1。

- 讀取服務把訊息寫入資料庫，並在同一個資料庫交易內為該對話排入一個延遲工作（見 ADR-0020）。
- 每個對話同一時間只有一個待處理的視窗。觸發條件三選一，先到先觸發：
  - 該對話安靜 45 秒；
  - 視窗累積 30 則訊息；
  - 視窗內最早的訊息已等待 3 分鐘。

  這三個數值是初始值，做成設定，依實際延遲與成本調整。
- 核心服務的 worker 處理視窗時，送給 LLM 的內容包含：
  - 視窗內的新訊息；
  - 同一對話較早的若干則訊息，作為前文；
  - 該對話既有的未完成 task（供判斷修改與取消，見 ADR-0008）；
  - 對話的中繼資料：對話類型、對方是否為新聯絡人、用戶的時區與目前時間。
- **一次 LLM 呼叫**同時輸出兩個結果，用 structured outputs 約束 schema：
  - 詐騙判定：是否可疑、手法分類、信心分數、給用戶看的簡短理由（見 ADR-0009）；
  - task 操作清單：新增、修改、取消，各帶信心分數與提醒時間（見 ADR-0008、ADR-0010）。
- 管線的 LLM 呼叫**不帶任何工具**。訊息內容是不可信的輸入，模型只能產出固定 schema 的資料，由程式決定後續動作。
- 處理失敗的工作重試；重試用盡的進失敗佇列，不阻塞同一用戶的其他對話。處理必須是冪等的：同一個視窗重跑不會產生重複的 task 或重複推播。

## 後果

### 正面

- LLM 看得到前後文，task 抽取較準、不容易重複建立。
- 呼叫量與群組訊息量脫鉤，洗版時成本可控。
- 管線模型沒有工具，訊息裡的 prompt injection 最多只能影響該視窗的判定結果，無法直接觸發系統動作。

### 負面與接受的風險

- 詐騙警告有延遲，一般情況在一分鐘內，持續洗版的對話最長約三分鐘。
- 視窗切分可能把同一件事切成兩半，靠「帶入既有 task」與前文來彌補。
- 一次呼叫做兩件事，prompt 較複雜；其中一項要調整時需要重跑整組 eval。
- 惡意訊息仍可能誘導模型把詐騙判成正常，或產生假的 task。高信心才自動進行事曆（ADR-0008）可以限制後者的影響。
