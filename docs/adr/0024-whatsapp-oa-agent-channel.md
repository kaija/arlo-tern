# ADR-0024：MVP 提供 WhatsApp 官方帳號 agent 通道，長結果導回 App，設預算上限

- 狀態：已接受
- 日期：2026-11-13
- 相關：ADR-0001、ADR-0011、ADR-0012、ADR-0013、ADR-0014、ADR-0022

## 背景

原始需求寫用戶除了 App，也可以透過 LINE 與 WhatsApp 的官方帳號跟 agent 對話。ADR-0011 與 ADR-0012 只涵蓋 LINE 官方帳號。ADR-0001 決定的「先 LINE、WhatsApp 後補」談的是**讀取個人對話**，不是 agent 的對話通道。

經確認，**WhatsApp 官方帳號的 agent 通道要在 MVP 內提供**。讀取個人 WhatsApp 對話仍然延後，兩者互不影響。

WhatsApp Business 平台與 LINE Messaging API 的差異（依 Meta 官方文件，2026-11-13 查閱）：

- **沒有短效的 reply token**。用戶傳訊或來電後開啟 24 小時的 customer service window，用戶再次傳訊就重新計時。視窗開啟期間可以發一般（非 template）訊息；視窗外只能發 template 訊息。
- **回覆要計費**。Meta 自 2026 年 10 月 1 日起恢復對 service message 逐則計費。每個商業電話號碼每月有 1,000 則已送達的免費 service message，第 1,001 則起收費。台灣屬於「Rest of Asia Pacific」計價區；該區的 service message 費率在另外的價目檔中，撰寫本文件時沒有查到數字。
- **用戶識別碼**。收訊 webhook 一定帶 business-scoped user ID；電話號碼在用戶設定了 username 時可能不提供。
- typing indicator 在回覆後或 25 秒後消失，以先到者為準；送出它的同時會把用戶的訊息標為已讀。

## 考慮過的選項

長任務的回覆方式：

1. **做完直接回在 WhatsApp**：不設時間期限，用到平台允許的能力，用戶不用離開 WhatsApp。
2. **比照 LINE**：約 50 秒內回得完就回，超過改 App push。兩個通道行為一致。
3. **長結果一律導回 App**：WhatsApp 只回短答案，長結果回一句摘要並請用戶到 App 查看。訊息則數最少。

超過免費額度的處理：

1. **設每月預算上限**：訂每月全域預算與每位用戶的每日則數上限，達到上限時請用戶改用 App。
2. **只用免費額度**：用完就停。但「額度已滿」的回覆本身也要計費，實際上用完後只能不回應。
3. **不設限，照實付費**：費率未明，且沒有上限。

## 決定

### 接入方式

- 使用 Meta 的 **WhatsApp Cloud API** 直連，不經 Business Solution Provider。
- webhook 由核心服務接收（見 ADR-0019），與 LINE webhook 並列。一律驗證 Meta 的簽章後才處理，並立即回應 HTTP 200，agent 在背景執行。
- 收到訊息後送出 typing indicator。

### 發訊邊界

與 ADR-0011 的原則一致：

- **只回覆用戶主動的提問**，而且只在 customer service window 開啟期間發送。
- **不發 template 訊息**，也就是不在視窗外主動聯絡用戶。
- 系統主動的通知（到期提醒、可疑訊息警告、連線失效）一律走 App push。

### 回覆方式：長結果一律導回 App

採用選項 3。這不是對齊過程中建議的選項（建議的是選項 1）。

- **短答案直接回在 WhatsApp**，盡量用單則訊息，例如查詢今天的 task、新增或修改一個 task、簡單問答。
- **長結果不在 WhatsApp 呈現**。符合下列任一條件視為長結果：
  - 建立 Trip，或大幅修改行程（新增或變動多個行程項目）；
  - 回覆內容超過長度門檻。門檻做成設定，初始值於實作時決定。
- 長結果的處理：完整內容寫進 App 內的 agent 對話與對應的資料（例如 Trip），WhatsApp 只回**一則**訊息，內容是一兩句摘要加上開啟 App 對應畫面的連結。
- agent 的處理時間不設 50 秒期限。處理較久時，完成後仍在 WhatsApp 回覆（短答案或摘要），因為 24 小時視窗內都可以發送。
- App 內的 agent 對話會顯示來自 WhatsApp 通道的這一輪問答，讓用戶回到 App 時看得到完整脈絡。
- **LINE 官方帳號的規則維持 ADR-0011 不變**。兩個官方帳號通道的回覆規則不同。

### 費用控管：每月預算上限

採用選項 1。

- 訂定**每月全域預算**（以訊息則數或金額表示）與**每位用戶的每日回覆則數上限**。兩個數值都做成設定，在查清台灣區費率後訂定初始值。
- 核心服務記錄每一則送出的 WhatsApp 訊息，供計數與對帳。
- 用戶達到個人每日上限，或全域預算用完時：回一則固定訊息請用戶改用 App。**同一個 customer service window 內只回這一次**，之後該用戶的訊息不再回應，直到上限重置。這則固定訊息本身也計入用量。
- 全域預算要保留一小部分給這類固定訊息；保留量也用完後，完全不回應。
- 用量達到預算的一定比例時發出內部告警。

### 帳號綁定

沿用 ADR-0012 的一次性綁定碼機制，差異如下：

- App 用 `wa.me` 連結開啟與官方帳號的聊天並預填含綁定碼的訊息，用戶按送出即可。
- **綁定的主鍵是 business-scoped user ID**，不是電話號碼，因為電話號碼不一定會提供。
- 不保存用戶的 WhatsApp 電話號碼；webhook 帶來的電話號碼用完即丟。
- 一個 App 帳號最多綁定一個 LINE 用戶與一個 WhatsApp 用戶，兩者可以同時存在。
- 未綁定的用戶傳訊時，回一則「請先在 App 內連結官方帳號」的固定訊息，同一個視窗內只回一次。這則訊息也計入用量；用量保護的優先順序高於回覆未綁定用戶。
- 綁定碼的有效期、一次性、雜湊保存、失敗限流等要求與 ADR-0012 相同。

### 記憶與對話

- App、LINE 官方帳號、WhatsApp 官方帳號三個通道共用同一份長期記憶，各自保留近期對話作為短期脈絡（見 ADR-0014）。
- agent 的工具與權限在三個通道完全相同（見 ADR-0013）。

## 後果

### 正面

- 滿足原始需求中的 WhatsApp 官方帳號通道。
- WhatsApp 訊息則數少，費用可預期且有上限。
- 長內容只在 App 呈現，行程這類結構化結果有較好的顯示與編輯介面。
- 不保存電話號碼，少蒐集一項個資。

### 負面與接受的風險

- 用戶在 WhatsApp 問了需要長回覆的問題，必須切到 App 才看得到完整結果，體驗有斷點。
- LINE 與 WhatsApp 兩個官方帳號通道的回覆規則不同，要各自實作與測試，也要各自向用戶說明。
- 「長結果」的判斷有模糊地帶，門檻需要依內測回饋調整。
- 達到上限後不回應，用戶可能以為服務壞了；固定訊息的文字要說明何時恢復。
- **每一則回覆都計入用量**，包含給未綁定用戶與已達上限用戶的固定訊息。陌生人大量傳訊可能消耗預算，因此需要「同一視窗只回一次」與用量保護。
- 多一個委外處理者：Meta 會處理用戶與 agent 在 WhatsApp 上的對話內容，包含 agent 回覆中的 task 與歷史訊息內容。需列入隱私政策（見 ADR-0022）。
- 使用 Cloud API 需要 Meta 的商業帳號、專用的電話號碼與顯示名稱等申請與審核作業，時程不由我方控制。具體要求要在申請時依當時的規定確認。
- 平台的計價規則近期才變動過，之後仍可能調整；預算與上限必須是可調的設定。

## 開工前要確認

- 台灣區（Rest of Asia Pacific）service message 的實際費率，用來訂定每月預算。
- Meta 商業帳號驗證、電話號碼與顯示名稱審核的要求與時程。
- `wa.me` 連結預填訊息在 iOS 與 Android 上的行為。
- 送出 typing indicator 會把訊息標為已讀，確認這對用戶體驗沒有不良影響。
