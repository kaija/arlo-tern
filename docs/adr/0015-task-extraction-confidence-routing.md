# 0015. Task 抽取：依信心分數分流，跨來源去重

- 狀態：已接受
- 日期：2026-11-07（2026-11-11 更新）

## 背景與問題

App 要顯示 AI 從用戶對話中找出的 task，並排到行事曆上。抽取可能出錯：誤判或時間理解錯誤。全部自動加入會讓行事曆充滿雜訊，全部要確認又太麻煩。同一件事也可能在多個來源出現，例如 email 與 LINE 都提到同一個會議。

## 考慮的選項

分流：

1. 一律進入待確認清單
2. 全部自動加入
3. 依信心分數分流

門檻：

1. 可設定，依用戶接受率校準
2. 固定門檻

去重：

1. 語意 + 時間比對後合併
2. 不去重，由用戶手動刪除

## 決策

- **抽取來源**：
  - 與 AI agent 的對話：App、LINE OA、WhatsApp 官方號。用戶可以選擇排除官方帳號上的對話
  - LINE 對話（linejs，見 [0009](0009-line-whatsapp-unofficial-read-only.md)）
  - WhatsApp 對話（whatsapp-web.js，見 [0009](0009-line-whatsapp-unofficial-read-only.md)）
  - Gmail 郵件（見 [0008](0008-gmail-access.md)）
- **分流**：每個抽出的 task 帶有信心分數
  - 高於門檻：直接加入行事曆
  - 低於門檻：進入 App 內的**待確認清單**，用戶確認後才加入
- **門檻**：
  - 做成可設定的值，初始值偏保守（大多數先進待確認清單）
  - 記錄用戶對每個 task 的接受 / 拒絕，定期依實際接受率調整
  - 不直接相信模型自評的分數
- **去重**：建立新 task 前，agent 查詢同時段既有的 todo / schedule（見 [0014](0014-personal-agent-shared-memory.md)），比對語意。判定重複就合併到既有 task，保留多個來源參照，不另外新增
- 每個 task 保留來源參照 ID（不保留原文，見 [0011](0011-no-raw-message-retention.md)），讓用戶知道 task 從哪裡來
- 抽取在 Processing worker 執行（見 [0002](0002-system-decomposition.md)）

## 後果

### 正面

- 明確的 task 不需要用戶操作，模糊的 task 不會直接污染行事曆
- 門檻依真實的接受率調整，比依賴模型自評可靠
- 同一件事不會在行事曆上重複出現

### 負面 / 風險

- 初期門檻保守，待確認清單會比較長
- 去重靠語意判斷，可能誤把兩件不同的事合併。用戶需要能拆開
- 每次抽取都要多一次查詢與比對，增加延遲與 LLM 成本

## 待決

- 門檻的初始值與調整週期
