# ADR-0020：資料與佇列只用 PostgreSQL

- 狀態：已接受
- 日期：2026-11-13
- 相關：ADR-0005、ADR-0007、ADR-0010、ADR-0015、ADR-0019、ADR-0021

## 背景

系統需要保存用戶、訊息、task、行程、記憶等資料，也需要佇列與排程：對話短視窗合併的延遲工作（見 ADR-0007）、管線工作、到期提醒（見 ADR-0010）、每日的保存期清除（見 ADR-0004）。

內測部署在單一 VM 上用 Docker Compose（見 ADR-0021），有狀態的元件越少越好。

## 考慮過的選項

1. **只用 PostgreSQL**：資料與 job queue 都在 PostgreSQL。
2. **PostgreSQL 加 Redis**（BullMQ）：佇列吞吐高、功能成熟，但多一個要維運與持久化的元件，訊息入庫與工作入列不在同一個交易內。
3. **PostgreSQL 加 SQS**（排程用 EventBridge Scheduler）：之後上 ECS 最順，但本機開發要模擬 AWS 服務，單機階段就綁進雲端託管服務。

## 決定

採用選項 1。

- **PostgreSQL 是系統唯一的有狀態元件**。
- 資料：用戶與登入、同意紀錄、LINE 連線與憑證、對話與訊息、task 與變更紀錄、提醒、Trip 與行程項目、agent 記憶與對話紀錄、推播 token、OA 綁定。
- 佇列與排程：用建在 PostgreSQL 上的 job queue 函式庫 **pg-boss**，涵蓋延遲工作、定時工作、重試與失敗佇列。
- 讀取服務寫入訊息與排入管線工作在**同一個資料庫交易**內完成，訊息入庫就一定有對應的工作。
- 每個對話同時只有一個待處理視窗（見 ADR-0007），用 job queue 的去重機制或資料表上的唯一約束實作。
- 中文關鍵字檢索用 PostgreSQL 的索引擴充套件（見 ADR-0015）。
- schema 與 migration 放在 monorepo 的共用套件（見 ADR-0019），兩個服務使用同一份。
- 資料存取一律帶用戶範圍條件；查詢層統一封裝，避免漏加條件造成跨用戶讀取。

## 後果

### 正面

- 單機部署只要顧一個資料庫：備份一份、還原一份、監控一份。
- 訊息入庫與工作入列有交易保證，不會漏處理。
- 本機開發只需要一個 PostgreSQL 容器。
- 轉 ECS 時直接換成 RDS PostgreSQL，應用程式不用改。

### 負面與接受的風險

- 佇列的吞吐受資料庫限制。內測的量遠低於上限，但用戶數成長後，job 資料表的膨脹與 vacuum 需要留意，屆時可能要把佇列移到專用的服務。
- 資料庫是單點：資料庫停擺時，讀取、管線、提醒、API 全部停擺。這在內測階段是已接受的（見 ADR-0021）。
- 延遲工作的觸發精度取決於 job queue 的輪詢間隔，提醒的發送時間會有數秒等級的誤差。
- 提醒排在很久以後（例如三個月後的繳費）時，是以長期存在的延遲工作保存，還是由每分鐘的輪詢從提醒資料表撈取，於實作時決定；兩者都只依賴 PostgreSQL。
- 資料庫保存明文的訊息與憑證（見 ADR-0005），所以資料庫的存取控管與備份保護是整個系統的安全關鍵。
