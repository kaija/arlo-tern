# ADR-0019：後端全 TypeScript，切成讀取服務與核心服務

- 狀態：已接受
- 日期：2026-11-13
- 相關：ADR-0001、ADR-0005、ADR-0007、ADR-0013、ADR-0020、ADR-0021、ADR-0024

## 背景

需求要求後端有一個獨立的 service 替用戶讀取訊息並處理。已選定的兩個關鍵函式庫都是 JS/TS：linejs（見 ADR-0001）與 OpenAI Agents SDK（見 ADR-0013）。linejs 要求 Node.js 22.18 以上或 24.11 以上（也支援 Bun 與 Deno）。

專案擁有者的慣例是複雜服務用 Python。需要決定後端的語言與服務切分。

## 考慮過的選項

1. **全 TypeScript，兩個服務**：讀取服務與核心服務。
2. **TS 讀取與 agent，Python 其餘**：符合 Python 偏好，但資料模型要在兩種語言各寫一份，agent 的工具要跨服務呼叫，兩套建置與測試流程。
3. **全 TypeScript，單一服務**：部署最簡單，但不符合「獨立 service」的需求，而且每次部署 API 都會中斷所有人的 LINE 連線。

## 決定

採用選項 1。這偏離了「複雜服務用 Python」的慣例，原因是兩個關鍵函式庫都只有 JS/TS 版本。

### Monorepo 結構

單一 repository，全部 TypeScript，執行環境為 Node.js 24 LTS：

```
apps/
  mobile/        Expo App（ADR-0018）
services/
  connector/     讀取服務
  core/          核心服務
packages/
  shared/        共用型別、資料庫 schema 與 migration、API 契約
```

### 讀取服務（connector）

- 常駐程序，持有每個已連結用戶的 LINE 連線（見 ADR-0001）。
- 職責只有四項：處理連結與中斷連結、接收訊息、依讀取範圍過濾（見 ADR-0003）、把訊息寫入資料庫並排入管線工作（見 ADR-0007）。
- **不呼叫 LLM、不發推播、不對外提供 API**。
- 啟動時從資料庫還原所有有效的 LINE session 並重新連線。重連要分批、帶隨機延遲，避免同時大量登入。
- 回報每個連線的狀態（已連線、重連中、已失效）到資料庫，供核心服務與 App 顯示。

### 核心服務（core）

- App 的 API（REST，agent 對話用 SSE）；
- LINE 官方帳號的 webhook（見 ADR-0011、ADR-0012）與 WhatsApp 官方帳號的 webhook（見 ADR-0024）；
- agent（見 ADR-0013）；
- 訊息管線 worker（見 ADR-0007）；
- 提醒排程與推播發送（見 ADR-0010、ADR-0018）；
- 保存期清除等背景工作（見 ADR-0004）。
- 同一份程式可以用 API 與 worker 兩種模式啟動，內測階段可以跑在同一個程序。

### 服務之間的溝通

- **資料面**走 PostgreSQL：讀取服務寫入訊息並排入工作，核心服務的 worker 取出處理（見 ADR-0020）。
- **控制面**（發起 QR 連結、回報 QR 與 pincode、中斷連結、變更讀取範圍）由核心服務透過只在內部網路開放的介面呼叫讀取服務。讀取服務不對外網開放任何埠。

## 後果

### 正面

- 只維護一種語言；App、兩個服務共用型別與 API 契約。
- 讀取服務可以獨立部署與重啟。部署核心服務不會中斷 LINE 連線；讀取服務被 LINE 改版弄壞時，App、agent、行事曆仍然可用。
- 讀取服務的職責很窄，容易審查「只讀不發」的約束。

### 負面與接受的風險

- 偏離 Python 慣例。之後若有報表、分析類的服務，仍可用 Python 另外開服務。
- 兩個服務共用同一個資料庫與 schema，schema 變更要同時考慮兩邊；migration 統一放在 `packages/shared`。
- 兩個服務共用資料庫，也代表核心服務被攻破時 LINE 憑證同樣暴露（見 ADR-0005）。
- 讀取服務是有狀態的常駐程序：重啟會讓所有用戶重新連線，連線數成長後需要分片，這不在 MVP 範圍。
- 讀取服務同一時間只能有一個實例持有某個用戶的連線，不能直接水平擴充成多副本。
